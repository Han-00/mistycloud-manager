# 网站分流、代理诊断与异常消耗

这三个入口已接入 Web 界面。源码版重启后生效；已有打包版需重新构建。玻璃版和经典版暂未增加对应页面。

## 指定网站直连或代理

1. 打开左侧「网站分流」，填写域名或 HTTP(S) 网站地址。
2. 选择「直连」或「代理」，点击添加；同一个域名再次添加会替换旧选择。
3. 点击「保存并应用」。代理运行时会短暂重启；已有长连接需要重新建立。
4. 用页面下方的域名预览检查**已保存规则**。修改草稿尚未保存时，预览仍使用旧规则。

填写 `example.com` 同时覆盖该域名及其子域名；`*.example.com` 也会规范为同样的域名规则。更具体的用户规则优先，例如：

| 用户规则 | 效果 |
|---|---|
| `qq.com` → 代理 | 覆盖内置的腾讯域名直连规则 |
| `download.qq.com` → 直连 | 在上一条范围内，单独让下载子域名直连 |

用户规则优先于内置规则和旧配置追加的直连域名。删除用户规则并保存后，下层规则重新生效。未命中上述规则时，预览显示「由引擎模板决定，当前未确认」；模板自身可能还有直连或其他路由，不能仅凭未命中就认定走代理。

系统代理的直连例外也会同步：如果一个宽范围例外与强制代理域名冲突，会移除该系统例外，让请求交给引擎判断；范围内其余国内域名的引擎直连规则仍保留。此行为适用于通过本工具代理端口的请求。应用自行配置的代理、VPN、直连或只有 IP 的请求，不能靠域名规则强制接管。

保存过程与换号、监控自愈共享运行守卫。规则应用、系统代理同步或落盘失败会恢复旧规则并报告结果；旧代理恢复失败时界面会明确提示。引擎未运行时只保存规则，不主动启动。切换页面保留草稿，「重新读取」会先提示是否丢弃未保存修改。

## 检查 Claude、Antigravity 等应用

1. 打开「代理诊断」，应用名可填 `Claude, Antigravity`，最多四项；按进程名匹配。
2. 可选填写目标域名，例如 `claude.ai`。输入完整网站地址时只保留主机名，不展示路径或查询参数。
3. 在目标应用中执行需要检查的操作，再点击采集。短连接可能已结束，可以在操作进行时重新采集。

页面同时展示三类证据，含义不同：

| 证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 域名规则、系统代理设置 | 保存的路由预期，以及 Windows 当前代理配置 | 不能证明桌面应用采用了系统代理 |
| 应用当前 TCP 连接 | 是否观测到应用连接本地代理端口；只有监听 PID、端口和地址与运行中的本引擎匹配，才确认连接本引擎 | 不能证明应用全部流量走代理，也不能定位到某次登录 |
| 引擎访问记录 | 最近被引擎接受的目标及出站路由选择，区分代理、直连和未知 | 不能证明请求成功，不能直接关联到某个进程或账号 |

「配置端口有连接，监听者未确认」表示还不足以确定连接本引擎。「当前无证据」表示采样时未捕获到连接；它不等于未使用代理。其他外部连接可能经过应用专用代理或 VPN，页面不会据此判定直连。旧访问记录会标注时间，未来或无法解析的时间保持未知。

采集只读取系统代理、进程名/PID、TCP 连接及本地引擎日志，不向目标网站发起请求，不读取应用命令行、环境变量或登录内容，也不替用户修改应用的代理设置。

引擎启动后将访问记录写入 `v2ray_work/access.log`。诊断读取末尾最多 64KB，并显示最近最多 20 条匹配记录；界面不展示原始日志、IP 目标地址或用户标识。重启时，超过 2MB 的访问日志轮换为 `access.previous.log`，保留一份旧日志。连续运行期间日志仍可能增长；此版本没有持续按大小轮换。

Windows 应用使用代理的方式并不一致，参考 [Microsoft 的 WinHTTP / WinINet 配置说明](https://learn.microsoft.com/en-us/windows/win32/winhttp/setting-wininet-proxy-configurations-in-winhttp)。[Claude Code 企业代理文档](https://code.claude.com/docs/en/corporate-proxy)描述的是 Claude Code 的代理配置，不能直接推断 Claude 桌面版的全部流量。Antigravity 的 [设置文档](https://antigravity.google/docs/settings)中沙箱网络选项的范围也不能用来证明整个桌面应用采用系统代理。

这些诊断提供连接和路由证据，无法确认某次账号限制的原因，也不能保证修改代理后不会被限制。平台限制应结合实际通知和 [Anthropic 官方执行说明](https://www.anthropic.com/transparency/system-trust-reporting)判断。

## 查看异常消耗

仪表盘的「异常消耗」卡片现在调用现有 `anomaly.detect()`，扫描近七天小时记录，最多展示消耗最高的 20 个时段，每 30 秒更新分析缓存。

- 单小时达到 200MB，并达到其他天同一小时平均用量的三倍，才提示同时命中阈值和历史基线。
- 同小时其他天样本少于两份时，仅按 200MB 阈值提示，并标明历史基线不足。
- 相关账号根据换号事件关联；桶内事件与根据较早事件推断的账号分开标注。这不是各软件的流量归因。
- 没有历史、未发现异常、分析读取失败有不同提示；坏小时记录会跳过，保留其余有效记录。

## 验证方式

新增测试使用临时配置、内存桥和模拟引擎，不触发真实账号注册、换号或目标站登录：

```powershell
python -m unittest discover -s tests -p test_routing_rules.py -v
python -m unittest discover -s tests -p test_proxy_diagnostics.py -v
python -m unittest discover -s tests -p test_web_network_features.py -v
python -m unittest discover -s tests -p test_switcher_runtime.py -v
python tests/check_v2ray_rules.py
node --check webui/app.js
```

`check_v2ray_rules.py` 使用本机引擎的 `-test` 模式检查两份临时配置，不启动监听。前端交互测试 `tests/_network_check.js` 需要本地静态 HTTP 服务、Playwright 和已安装的 Chromium，覆盖规则编辑、保存反馈、页面切换、诊断证据、异常提示及深浅主题；它使用模拟桥，不能代替真实桌面应用或网站登录验证。
